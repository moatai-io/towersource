# Agent 권한과 연결 운영 매뉴얼

## 1. 핵심 원칙과 적용 범위

**사용자는 Agent에 접근하고, Agent는 자신의 프로젝트·도구·연결 범위로 업무를 실행합니다.** 요청자의 개인 Google 로그인이나 플랫폼 관리자 권한을 Agent가 자동으로 물려받지 않습니다.

이 문서는 Agent 중심 권한 정책과 관련 구현을 설명합니다. 서버에 해당 코드·DB migration·실행 설정이 함께 적용되어야 합니다. 문서를 갱신했다는 사실은 배포 완료를 의미하지 않습니다. 아래의 운영 전환 조건을 확인하십시오.

## 2. 역할은 무엇을 의미하나요?

| 역할 | 업무 범위 | 자동으로 생기지 않는 권한 |
|---|---|---|
| member | 접근 가능한 Agent에서 일을 요청하고, 실제 프로젝트 쓰기 권한에 따라 파일·Agent 연결을 관리합니다. | 읽기 전용 프로젝트의 수정, 다른 Agent 접근, 플랫폼 관리 권한은 생기지 않습니다. |
| operator | 회사 Agent·업무 자원·연결을 관리하고, Operator access를 켜거나 끄고 해당 Agent로 호스트 작업을 실행합니다. | 개인 비공개 본문 열람, 타인 명의 실행, admin/operator 승격, 타인 비밀번호 재설정 권한은 별개입니다. |
| admin | 플랫폼 설정과 인프라를 관리합니다. | admin의 요청이라고 일반 Agent에 호스트 실행 권한이 추가되지는 않습니다. |
| viewer / guest | 부여된 읽기·공유 범위로 접근합니다. | 화면이나 경로가 보인다고 수정·삭제할 수 있는 것은 아닙니다. |

역할만으로 모든 작업을 판단하지 않습니다. 현재 계정 상태, 프로젝트 멤버십과 쓰기 권한, 세션 소유권, Agent 상태 및 실행 설정을 함께 확인합니다.

## 3. 개인 대화와 Agent 업무 자원의 차이

- 개인 비공개 세션의 본문은 회사 관리자라는 이유만으로 열람할 수 없습니다. 공유나 별도의 접근 근거가 필요합니다. 플랫폼 admin은 별도의 관리 권한이 있으므로 이 보호를 모든 관리자에 대한 암호학적 비공개 보장으로 해석하면 안 됩니다.
- 프로젝트 파일과 Agent 연결은 업무 자원입니다. 비공개 세션에서 요청했더라도 결과를 프로젝트 파일로 저장하면 해당 파일의 프로젝트 접근 정책을 따릅니다.
- 대화를 읽을 수 있는 것과 다른 사람의 세션에 메시지를 보내거나 실행 설정을 바꾸는 것은 다른 권한입니다.
- 개인 메모·개인 파일은 프로젝트와 별도의 저장 경계에 있습니다. 프로젝트로 복사하거나 공유할 때 대상과 범위를 확인하십시오.

## 4. 회사 관리자의 명시적 참여

지원되는 프로젝트 화면에서 회사 관리자는 참여 사실을 확인하고 참여하거나 해제할 수 있습니다. 참여는 일반 멤버십과 별도로 기록되며 감사 기록과 Notification Center 알림을 함께 저장합니다.

참여하더라도 개인 비공개 본문이나 타인 명의 메시지 전송 권한은 생기지 않습니다. 역할 강등·비활성화 시 참여가 종료되며 재승격만으로 이전 참여가 부활하지 않습니다.

주의 사항:

- 이 안내는 프로젝트 참여 UI를 기준으로 합니다. 채널 참여 API가 있다는 이유로 퇴역한 채널 화면이 복구된 것은 아닙니다.
- 참여 알림의 실시간 WebSocket·브라우저 push 전달까지 보장하지 않습니다.
- 접근 회수 후 이미 실행 중인 외부 작업을 되돌리거나 즉시 취소한다고 보장하지 않습니다.

## 5. Connection은 누구의 자원인가요?

**Connection은 사용할 외부 계정과 사용 범위를 나타내고, Credential은 그 연결에 필요한 비밀값입니다.**

| 연결 범위 | 의미 | 등록 전 확인 |
|---|---|---|
| Agent 전용(project) | 해당 Agent의 업무에 사용할 연결입니다. | 그 Agent를 사용하는 사람이 이 계정으로 업무를 맡겨도 되는지 확인합니다. |
| 회사 공용(workspace) | 회사가 여러 Agent에서 사용하는 공용 연결입니다. 일반 프로젝트에 자동으로 제공되는 범위입니다. | 회사 공유가 의도인지 확인하며, 특정 Agent에만 제한하려면 Agent 전용 연결을 사용합니다. |
| 기존 개인 연결 | 과거 사용자 중심으로 저장된 연결입니다. | 새 Agent 실행에 자동 상속하지 않습니다. 계정 소유자 동의와 명시적 등록·이관이 필요합니다. |

개인 계정을 공유 Agent에 연결하면 그 계정은 해당 Agent의 업무 자원으로 사용됩니다. 개인 비공개 세션만 사용한다고 연결까지 개인 전용으로 바뀌지는 않습니다. 연결 관리 권한과 실제 작업 요청 권한은 구분되지만, 연결 사용을 매번 요청자의 개인 자격증명과 결합하는 모델은 아닙니다.

비밀값은 채팅·Git·일반 문서에 기록하지 말고 안전 입력 흐름을 사용하십시오. 연결을 끊더라도 이미 전송한 메일이나 외부 변경이 취소되지는 않습니다.

## 6. Google Workspace 사용 절차

1. 작업할 Agent를 선택합니다.
2. Agent Connections에서 업무에 사용할 Google 계정을 명시적으로 연결합니다. 다른 사람의 계정이나 기존 개인 연결을 동의 없이 공유하지 않습니다.
3. 연결이 여러 개면 의도한 연결 ID 또는 기본 연결을 지정합니다.
4. 인증 상태와 최소 읽기 전용 API로 연결을 확인합니다.
5. 메일 발송·일정 생성·파일 수정 전에는 실행 계정과 대상을 확인합니다.

기본 선택 순서는 **명시한 연결 ID → 하나의 Agent 기본 연결 → 사용 가능한 유일한 연결**입니다. 기본 연결이 여러 개이거나 후보가 여러 개인데 기본값이 없으면 임의 선택하지 않고 오류를 반환합니다.

지원되는 실행 도구에서 직접 `gws` 명령을 사용하십시오. 명시적 계정 선택 예시는 다음과 같습니다. `gws-work`는 예시 ID이며 실제 등록된 ID로 바꿔야 합니다.

```bash
GWS_CONNECTION_ID=gws-work gws auth status
GWS_CONNECTION_ID=gws-work gws gmail users getProfile --params '{"userId":"me"}'
```

`gwsConnectionId`를 지원하는 실행 API는 해당 필드로도 연결을 지정할 수 있습니다. 임의 wrapper 내부 실행은 인증 자동 주입이 되지 않을 수 있습니다. 상태 조회만으로 인증 성공을 단정하지 말고 요청 범위의 최소 API를 확인하십시오.

### 제거되는 동작

- `GWS_PROFILE=personal`로 요청자의 개인 인증을 가져오는 동작은 지원하지 않습니다.
- Agent 작업 안에서 `gws auth login`이나 옛 호스트 OAuth callback으로 개인 로그인을 만들지 않습니다.
- 기존 `users/<id>` 인증 묶음을 요청자에 따라 선택하거나 Agent 기본 계정으로 조용히 대체하지 않습니다.
- 원격·호스트 경로의 기존 `finance` 별칭은 기본 계정으로 대체하지 않고 명시적 연결 선택을 요구합니다. 로컬 legacy 별칭이 남아 있더라도 새 업무 절차에는 연결 ID를 사용하십시오.

## 7. 오류가 나면 어디를 확인하나요?

| 오류·상태 | 의미 | 다음 조치 |
|---|---|---|
| `PROJECT_GWS_CREDENTIAL_NOT_AVAILABLE` | 선택 가능한 Agent 연결이 없거나 실행용 값을 확인할 수 없습니다. | Agent 연결과 실행 시 주입 상태를 확인합니다. |
| `GWS_CONNECTION_NOT_ALLOWED` | 지정한 연결이 이 Agent에 허용되지 않습니다. | ID와 연결 범위를 확인합니다. 다른 계정으로 임의 재시도하지 않습니다. |
| `AMBIGUOUS_GWS_CONNECTION` / `AMBIGUOUS_GWS_DEFAULT` | 기본 계정을 안전하게 결정할 수 없습니다. | 연결 ID를 명시하거나 기본 연결을 하나로 정합니다. |
| `AGENT_GWS_CONNECTION_REQUIRED` | 개인 프로필 또는 Agent 내부 로그인 요청입니다. | Agent Connections로 연결한 후 개인 프로필 없이 실행합니다. |
| `AGENT_GWS_ACCOUNT_MIGRATION_REQUIRED` | 기존 다중·개인 계정 묶음 또는 안전하게 읽을 수 없는 인증 묶음입니다. | 계정 소유자 동의를 받아 재연결·이관합니다. 파일 이름만 바꿔 공유하지 않습니다. |
| `AGENT_GWS_EXPLICIT_CONNECTION_REQUIRED` | 해당 실행 경로에서 legacy 별칭을 해석하지 않습니다. | 별칭을 제거하고 Agent 연결 ID를 지정합니다. |
| `AGENT_EXECUTION_PLANE_UNAVAILABLE` | 프로젝트 실행 환경이 없고 현재 역할·Agent 설정도 호스트 실행을 허용하지 않습니다. | admin·operator는 Agent의 Operator access와 활성 상태를 확인합니다. 일반 Agent는 프로젝트 실행 환경을 확인합니다. |
| Provider의 401 / 권한 부족 | 실제 서비스가 인증 또는 요청 권한을 거부했습니다. | 연결 설정 → 이번 실행의 주입 → Provider 수락을 순서대로 확인합니다. |

메일·일정 등 외부 쓰기 실패 후에는 기존 요청의 성공 여부부터 확인하십시오. 인증을 바꿔 무조건 재시도하면 중복 발송·생성이 발생할 수 있습니다.

## 8. 플랫폼 관리자 전환 체크리스트

아래는 운영 서버 변경 승인이 아니라 적용 전 확인 목록입니다.

- [ ] 관리자 참여 migration 194를 실제 PostgreSQL에서 검증하고 코드와 함께 적용할 계획을 마련합니다. 테이블 없이 새 코드만 배포하면 목록·검색이 실패할 수 있습니다.
- [ ] admin·operator가 Agent의 Operator access를 설정하고 사용할 수 있는지 확인합니다. 별도 서버 허용 목록이나 추가 승인은 필요하지 않습니다.
- [ ] 개인·다중 계정 GWS 묶음과 호스트 인증에 의존한 업무를 식별하고 동의를 받아 이관합니다. 실제 인증 파일을 일반 문서로 복사하지 않습니다.
- [ ] 기존 Agent 저장 경로가 플랫폼 저장소·보호 시스템 경로 아래에 있어 회사 관리자 접근이 차단되는지 확인합니다.
- [ ] member의 정상 업무, 읽기 전용 사용자의 거부, operator의 명시적 참여, 개인 비공개 보호를 실제 환경에서 확인합니다.
- [ ] 여러 서버의 권한 회수 지연과 스트리밍 부하를 검증합니다. 교차 프로세스 인증 캐시는 지연될 수 있으며 즉시 전역 회수를 보장하지 않습니다.
- [ ] 예약·실행 중 작업·다른 엔진·비-bash 도구를 별도로 확인합니다. 단위 테스트 통과를 OS·마운트 격리의 증명으로 취급하지 않습니다.
